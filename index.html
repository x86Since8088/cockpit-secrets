Safe

The passphrase is asked for every time a safe is opened. There is no “remember” option here and nowhere to put one: one unlock lives inside one short-lived helper process, and closing this page, locking, or letting the session expire ends it.

Nothing about a safe is kept in this browser. The passphrase goes into one variable, is written to the helper’s standard input, and is overwritten. No browser storage area, no cookie and no hidden field is used.

Copying to the clipboard is best-effort. The clipboard is a shared operating-system resource: this page clears it when the countdown ends and when the page is hidden, but another application may already have read it, and a clipboard manager may keep its own copy that this page cannot reach.

An export is plaintext on disk, and it stays there. Exporting writes every password in a safe, unencrypted, into a file the helper chooses; the countdown that re-hides a revealed value has no equivalent for a file. This page never shows an export’s contents — it reports only where the file landed and how big it is — and deleting it afterwards is the operator’s job, not this page’s. An attachment downloaded from an entry, by contrast, is streamed through the Cockpit channel straight to this browser and never lands on the server’s disk.

Uploading a safe sends the encrypted file first and asks for the passphrase last. The file is staged, its header is read back to you — format, version, cipher and KDF, which are not secret and are readable by anyone holding the file — and only then are you asked to unlock it. That summary is read from the header and is not authenticated: nothing has been checked against a passphrase at the point you see it. A file that does not open with the passphrase you give is never registered and never lands anywhere, and a wrong passphrase does not throw the upload away.

This page never sends a path. Creating or uploading a safe supplies an id; the helper mints the filename and chooses the directory from the access class. There is no control here, on any dialog, for a path, a filename or a directory.

Forget leaves the file; Delete destroys it. Forgetting a safe removes its registry entry and nothing else — the encrypted file and its backups stay exactly where they are, and registering it again brings it back. Deleting destroys the file and its whole backup ring, is behind typing the safe’s id, and cannot be undone. Overwriting a file before unlinking it is best-effort: on an SSD, a copy-on-write filesystem, or anything already in a snapshot or a backup, the old bytes may still be recoverable.

A safe held open by the agent is announced, always. When a safe is unlocked through secrets-agent, the banner at the top of this page names it and counts down to its automatic lock, from every view. If that banner is not there, nothing is being held — the agent is off unless a registry entry opts in, and there is nothing for it to hide.

What is greyed out here is decoration. The helper re-derives the caller’s identity from the kernel and re-checks the access class on every verb; that is what refuses a safe you may not open, not this page.
